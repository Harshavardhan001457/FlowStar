# Measurement definitions

The baseline simulation writes measurements to `results/baseline/`. All
timestamps are simulation time in seconds. The output is generated by the
NS-3 run; no values are synthesized.

## `flow_statistics.csv`

This file contains one row for each expected TCP data flow. FlowMonitor
provides the packet and byte counters at the IPv4 layer. Its `tx_*` and
`rx_*` fields include IP-layer packet/byte accounting, not just the
application payload counted by `PacketSink`.

Columns:

- `flow_id`: `flow1`, `flow2`, or `flow3`.
- `source_ip`, `destination_ip`, `source_port`, `destination_port`,
  `protocol`: the FlowMonitor IPv4 five-tuple.
- `tx_packets`, `rx_packets`, `tx_bytes`, `rx_bytes`: FlowMonitor IP-layer
  counters.
- `average_delay_s`: `delaySum / rx_packets`, in seconds. This is an average
  over received IP packets.
- `packet_delivery_ratio`: `rx_packets / tx_packets`, or `0` when no packets
  were transmitted.
- `lost_packets`: FlowMonitor's loss estimate after its lost-packet check.
  This is not a claim that every lost packet was dropped by the bottleneck
  queue.
- `first_tx_time_s`, `last_rx_time_s`: FlowMonitor packet timestamps.
- `average_throughput_bps`: `rx_bytes * 8 / (last_rx - first_tx)`, using the
  FlowMonitor interval for that flow.
- `application_rx_bytes`: the corresponding `PacketSink::GetTotalRx()` value.

The FlowMonitor values are IP-layer measurements; `application_rx_bytes` is an
application-payload measurement and should not be treated as interchangeable
with `rx_bytes`.

## `throughput_timeseries.csv`

The sampler reads each `PacketSink` counter every 0.1 seconds by default.
Rows use the **end** of the interval as `time_s`. The first sample establishes
the previous counter and therefore does not produce an invalid zero-duration
row. Each subsequent row contains:

`interval_throughput_bps = interval_rx_bytes * 8 / interval_duration_s`

The final partial interval is sampled at the configured simulation stop time.
`cumulative_rx_bytes` and `interval_rx_bytes` are application bytes.

## `queue_timeseries.csv`

The two actual `Queue<Packet>` objects attached to the bottleneck
`PointToPointNetDevice`s are sampled every 0.1 seconds. `occupancy_packets`
and `occupancy_bytes` are the queue's current state, not an estimate based on
throughput. `configured_limit_packets` is the configured DropTail limit of
100 packets. The queue identifiers represent the left-to-right and
right-to-left bottleneck directions.

## `packet_drops.csv`

Rows are generated by the bottleneck queue `Drop` trace source and contain
simulation time, direction, trace source, and packet size in bytes. An empty
data section means no bottleneck queue drop event occurred during the run.
FlowMonitor lost packets remain a separate metric and are not reclassified as
queue drops.

## `run_metadata.json`

Metadata records the NS-3 version, actual simulation/application timing
configuration, TCP variant, bottleneck settings, queue limit, sampling
interval, timestamp convention, and the run's fairness definition.

The fairness index is Jain's index:

`J = (sum(x_i)^2) / (n * sum(x_i^2))`

where `x_i` is each flow's application bytes received divided by the common
sender interval (1 to 19 seconds by default). This is one aggregate value,
not a claim about fairness at every instant. A zero-throughput run is represented as JSON `null`; the normal baseline run
has nonzero reception on every flow.

When `dynamicQueueAssignment=true`, the run also writes
`dqa_queue_timeseries.csv` and `dqa_assignments.csv`. These describe two
software QueueDisc internal queue classes per bottleneck direction. They are
logical queue resources, not additional physical point-to-point device queues
or hardware virtual lanes. The DQA files do not replace the existing
`queue_timeseries.csv` or `packet_drops.csv` definitions.

When `hybridPerFlowState=true` is also enabled, the run writes
`hybrid_state.csv`. This records per-flow logical assignment lifecycle events,
dedicated-resource counts, and shared-fallback counts. A hybrid assignment is
software state associated with the existing QueueDisc classes; it is not a
claim that each flow owns a physical queue.

## Reproduction

The source is compiled with the NS-3.48 wrapper and run with the project as
the working directory so relative output paths stay under this project:

```bash
cp scratch/flowstar-baseline.cc /home/harsha/Projects/ns3/ns-3.48/scratch/flowstar-baseline.cc
cd /home/harsha/Projects/ns3/ns-3.48
./ns3 build flowstar-baseline
./ns3 run --cwd /home/harsha/Projects/FlowStar flowstar-baseline --no-build
```

The temporary NS-3 scratch copy is only needed because this project keeps its
source outside the NS-3 source tree; it does not modify NS-3 itself.
